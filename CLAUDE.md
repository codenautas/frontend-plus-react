# CLAUDE.md — frontend-plus-react

Librería React (MUI + react-data-grid) para consumir backends hechos con `backend-plus` sin reescribir el frontend de cada aplicación: login, menú, grillas editables de cualquier tabla (con sus detalles anidados), formularios de procedimientos y editor vertical. Cada aplicación aporta solo lo propio (wScreens, clientSides, resultados de procedimientos) mediante `extendWScreens`, `extendClientSides` y `extendResultsOk`.

Se consume desde las aplicaciones (`mi-frontend`, `dmencu-frontend`, y las que vengan) como paquete npm o enlazado con `npm link`. Esta librería **no** es el frontend de `backend-plus` (ese es el que sirve el propio framework con `my-tables.js`): reproduce su comportamiento. Ante la duda de cómo debe comportarse algo, la referencia es `backend-plus` (`for-client/my-tables.js`, `unlogged/my-ajax.js`) y los `.d.ts` en `node_modules/backend-plus/lib/backend-plus.d.ts`.

## Reglas de código

Son las de `dmencu` (que aplican a todo proyecto compartido de esta carpeta), escritas acá porque esta librería no depende de `dmencu` y no puede importar su `CLAUDE.md`:

- **Todos los tipos explícitos.** Prohibido `any`, `@ts-ignore`, casts vía `unknown` o magia sin justificación. Hoy el código no tiene ninguno y tiene que seguir así. Si un callback recibe un parámetro, tiparlo.
  - Lo que viene del servidor o de un catch es `unknown`: `mensajeDeError(err)` para el mensaje de un error y `requerido(valor, 'qué faltó')` para algo que tiene que existir (ambos en `utils/errores.ts`). Las filas son `FilaDeDatos`; las filas de resumen (filtros y totales), `FilaDeResumen`; los parámetros de un procedimiento, `ParametrosDeProcedimiento`.
  - `callApi<R>(...)` lleva la forma del resultado de ese procedimiento; la única afirmación de tipo sobre lo que manda el servidor está en `resultadoDeProcedimiento` (`utils/fetchApi.ts`).
  - `type-store` no publica tipos: están declarados en `src/types/type-store.d.ts`, escritos para mudarse tal cual a `types.d.ts` (`modules/type-store/index.d.ts`). Las columnas propias se distinguen con `esColumnaPropia` y `customType`, no con casts.
  - Una excepción acotada: los tests usan dobles de los eventos de react-data-grid con una aserción de tipo, en un único helper por archivo.
  - Si una `interface` no cabe en `FilaDeDatos` (`Record<string, unknown>`), es porque las interfaces no tienen firma de índice: usar `type`.
- **Preservar el estilo existente** y **no tocar el formato de lo que ya existe**: el diff muestra solo las líneas que cambian de verdad. Sin reindentar, sin tocar espacios finales, sin agregar ni quitar el salto de línea final.
- **Respetar el fin de línea de cada archivo**: hay archivos con CRLF y otros con LF. Las líneas nuevas llevan el mismo que el resto del archivo (`git ls-files --eol <archivo>`). No editar con `sed -i` ni con herramientas que reescriban el archivo entero. Antes de commitear, `git diff --stat` tiene que coincidir con `git diff --ignore-all-space --ignore-cr-at-eol --stat`; si no, hay formato que revertir.
- **Nombres de dominio, funciones, variables y comentarios en castellano** (consistente con las aplicaciones y las bases). Los identificadores que son API de terceros se dejan como están.
- **Compilación sin fallbacks**: `npm run build` y `npm run typecheck` no toleran errores; no agregar `|| echo ...` a los scripts. Un error de tipos se corrige en el código.
- `npm install` reordena y reformatea todo `package.json`. Después de instalar algo, restaurar el archivo y agregar a mano solo la línea nueva (el `package-lock.json` sí lo maneja npm).

## Estructura

## Cosas que no son obvias (y se rompieron antes)

### Protocolo con el backend
- Cada parámetro viaja codificado según su `encoding` en `client-setup` (`JSON4all` por omisión, `plain`, `JSON`), igual que `my-ajax.js`; el servidor decodifica con el mismo encoding. Mandar `JSON.stringify` o texto crudo rompe fechas (llegan como string) y convierte textos como `"5"` en números. Los procedimientos `method:'get'` van por la URL.
- El resultado puede traer líneas de progreso antes de `--`; `parseBackendResponse` se queda con la última parte.

### Rendimiento de la grilla
- Las **columnas** (`useGridColumns`) no pueden depender de datos, feedback, orden ni filtros: si cambian en cada edición, react-data-grid redibuja todas las celdas. Lo que cambia por celda va al `EstadoGrilla`; la celda (`CeldaDato`) es un componente memorizado que se suscribe solo a lo suyo.
- No copiar las filas en cada render (`rows.map(...)`): anula la memorización de filas. El estilo por fila va por `rowClass`.
- No reemplazar la grilla por un spinner mientras hay una llamada en curso; el spinner es solo para la carga inicial.
- `useGridDataView` deja en su lugar la fila editada cuando cambian pocas filas (no reordena ni vuelve a filtrar en medio de una edición) y recalcula todo cuando cambia mucho (refrescar, importar).
- Las grillas se cargan con una sola petición por tabla y filtros aunque React monte los efectos dos veces (`cargasEnCurso`).

### Scroll de la página
- `html`, `body` y `#root` tienen `overflow: hidden` a propósito (las grillas toman el alto que queda de la ventana). El que scrollea es el contenedor que `MainLayout` pone dentro de `<main>`, **debajo** de un `<Toolbar />` espaciador (mide lo mismo que el de la AppBar en cualquier tamaño de pantalla). Una pantalla más alta que la ventana (una wScreen, un formulario de procedimiento, las pantallas de `backend-plus` como el tablero de dmencu) queda recortada si ese contenedor no scrollea. Y el área que scrollea no puede empezar en el borde de la ventana: la AppBar (fija) taparía la flecha de arriba de la barra de desplazamiento. No usar `theme.mixins.toolbar.minHeight` como margen: es solo el valor base (56 px) y la barra mide 64 px desde 600 px de ancho.
- Las grillas no deben generar una barra de más: en una página de grilla, `scrollHeight` del contenedor mayor que su `clientHeight` es un error del cálculo de alto de la grilla. Esto no se puede probar en jsdom: se mide en el navegador.

### Edición y teclado
- **La celda está tipada como en `backend-plus`** (`utils/typedControls.ts`). Allá la celda numérica es un `<input type=number>` y `rejectedChar` del typer corta en el teclado lo que el tipo no admite; acá el editor es de texto y `getBestTypedValue` convertía en `null` lo que no era un número, sin avisar: «abc» en un entero borraba el valor o, si ya estaba vacío, «no cambió» y no se guardaba nada (`result_sup` en `edicion_tem`). Ahora el editor no deja escribir los caracteres que el tipo rechaza (`caracterRechazado`: en un entero solo dígitos y «-»; en una referencia abre el menú) ni pegar texto que los tenga (`textoPegadoRechazado`), y al guardar `tiparEntrada` avisa (cartel y celda en rojo) si lo escrito no es un valor del tipo (una fecha que no existe, por ejemplo). Un texto de solo espacios en un número o una fecha es vacío. Con `nullable` sin declarar el vacío de un entero es 0 (`emptyValue` del typer).
- **El clic afuera de la grilla guarda**, como Enter, Tab y las flechas: es el `blur` del editor (`handleBlur`). Las columnas ponen `commitOnOutsideClick: false`: con el valor por omisión react-data-grid cierra el editor por su cuenta, sin guardar lo que se escribió, y además los menús de F9 (un modal fuera de la grilla) cuentan como «afuera».
- Al editar con un filtro activo, react-data-grid entrega solo las filas visibles: `handleRowsChange` reemplaza las filas editadas dentro de `tableData`, nunca lo pisa con lo recibido.
- **Las teclas de una celda en edición reproducen a `backend-plus`** (`captureKeys` de `my-things.js`), en `hooks/grid/teclasDeCelda.ts` (`direccionDeSalida`) y `useGridEvents.handleKeyPressInEditor`. Dejar la celda por cualquier camino la guarda. Enter y Tab van a la celda editable siguiente (al final de la fila, a la primera de la de abajo); Shift+Tab a la anterior; ↑ y ↓ a la misma columna de la fila de arriba o de abajo, siempre; ← solo si el texto está vacío o el cursor está al principio; → solo si el texto está vacío o si la tecla anterior también fue → con el cursor al final (hay que apretarla dos veces: la primera solo llega al final). Con Ctrl, Alt o Meta (o Shift en las flechas) ninguna deja la celda. Una flecha que solo mueve el cursor **no guarda ni cierra el editor** (antes cualquier flecha lo hacía). `handleKeyPressInEditor` devuelve si la resolvió la grilla y el editor entonces cancela el efecto nativo: sin eso el Tab del navegador mandaba el foco a un botón de otra fila.
- **No esperar la respuesta del servidor para mover el foco** (Enter, Tab, flechas, F4): con la tecla apretada llegan más pulsaciones que respuestas. El cambio de la fila se aplica en el acto y el guardado sigue en segundo plano.
- **No llamar `onRowChange(fila, true)` del editor después de un `await`**: cierra el editor de la celda que esté seleccionada en ese momento (la siguiente). La fila que devuelve el servidor se aplica sobre los datos (`setTableData`).
- F4 con la tecla apretada: las pulsaciones que caen en la celda antes de que el editor nuevo tenga el foco se le pasan por `registrarEditor`, o quedan en cola hasta que haya uno. F4 usa el valor que acaba de copiar si la fila de arriba todavía no se redibujó.

### Detalles desplegados (como `backend-plus`)
- **El botón del detalle**: Ctrl+clic o la ruedita lo abren en otra pestaña. La ruedita llega como `auxclick`, y en Windows el navegador empieza el desplazamiento automático al apretarla y no lo manda: el botón cancela el `mousedown` del botón del medio. El botón se centra sobre toda la celda (`position: absolute; inset: 0`): la columna mide 30 px y la grilla le deja 8 px de margen a cada lado, así que centrarlo dentro del margen lo corría a la derecha de su sigla.
- Un detalle es una fila especial (`FilaDetalle`, marcada con un `Symbol`) que se intercala debajo de su fila y ocupa todas las columnas; adentro hay otra `GenericDataGrid` (recursiva). Ctrl+click o botón del medio lo abre en otra pestaña.
- Alturas: **de arriba hacia abajo**. La grilla principal toma lo que queda de la ventana; cada detalle recibe `altoDisponible` y no puede pasar de ahí, así su pie queda visible. No calcular el tope con el alto medido de la grilla padre: una grilla de pocas filas es baja y aplasta a su detalle.
- Un detalle con muchas filas muestra `firstDisplayCount` (20) cuando supera `firstDisplayOverLimit` (30), los mismos umbrales de `backend-plus`, y **virtualiza** sus filas; los chicos crecen según su contenido. La grilla principal siempre virtualiza.
- Anchos: una grilla anidada es tan ancha como sus columnas; si un detalle abierto es más ancho, informa su ancho hacia arriba y el padre se ensancha.
- Un cache compartido por la jerarquía (`CacheGrillasContext`) permite volver a mostrar un detalle que salió de pantalla por la virtualización sin pedirlo otra vez.
- El título de una grilla anidada es el de su tabla, igual que el de la principal.
- **Detalle `wScreen`** (`{wScreen:'ticket', fields:[...]}`, como las anotaciones de un ticket en gestik): se dibuja la pantalla registrada en `myWScreens` y recibe `params` (los fixedFields del detalle como objeto plano, igual que `mainAction(params, div)` de backend-plus). La fila toma el alto de lo que la pantalla dibuja, hasta el máximo disponible, y scrollea por dentro. Las grillas que la pantalla arma (`<GenericDataGrid anidada .../>`) reciben ese máximo por `AltoDisponibleContext`. Con Ctrl+click o el botón del medio se abre en otra pestaña, en `/wScreens/<nombre>?campo=valor` (`PantallaDeRuta` pasa la query string como `params`).
- **`condition`** de un detalle: el nombre de una función registrada en `myConditions` (o `extendConditions`) que recibe la fila y dice si se muestra el botón; sin ella o si da falso, la celda queda vacía. Si el nombre no está registrado se avisa una vez por consola y se muestra el detalle.
- Lo que aporta la aplicación (`myWScreens`, `myClientSides`, `myResultsOk`, `myConditions`) se registra **antes del primer render**, no en un efecto: las rutas de las wScreens se arman al renderizar a partir del registro.
- El `ff` de un ítem de menú puede ser un arreglo `[{fieldName, value}]` (lo que documenta backend-plus) o un objeto `{campo: valor}` (lo que usa dmencu); `fixedFieldsDeMenu` entiende los dos.

### Guardado en otras tablas (campos con `table`)
- Una definición puede mostrar campos que se guardan en otra tabla (`table` en el `fieldDef`, con `nameForUpsert` y `sql.otherTableDefs`; ejemplos: `sensibilizado` de `grilla_hoja_ruta` en ggs, las asignaciones de `areas_asignacion_general` en dmencu). Lo reparte el servidor en `table_record_save`; el cliente tiene que mandar **igual que `backend-plus`** (`saveRecord` de `TableConnector`), y acá se rompió de dos maneras (`useTableRecordSave.ts`):
  - `newRow` en un update lleva **solo lo que cambió**; la clave viaja aparte en `primaryKeyValues`. Si `newRow` lleva también la clave, el servidor se la asigna a la tabla principal y esta queda con un update de solo claves: «se detectó una orden de modificación sin columnas a modificar».
  - `table` es `tableDefinition.name` (`depot.def.name`), **no** `tableName`: una definición como `areas_asignacion_general` tiene `tableName: 'areas'` (la física) y el servidor busca la definición por el nombre que recibe; con el de la física no encuentra los campos («field _encu does not exist in areas»).
- Probado contra ggs (con una copia de `dmencu`): `sensibilizado` (boolean, se escribe `sí`) y el `encu` de la asignación general; los valores de prueba se restauraron.

### Expanders (F9 o Alt+↓, como `backend-plus`)
- En `backend-plus` **F9** o **Alt+↓** en una celda abren el «expander» del tipo (`TypedControls.Expanders`, en `typed-controls`). Acá están todos (`utils/expanders.ts`, `tipoDeExpander`, en el mismo orden en que los prueba backend-plus): JSON de solo lectura, referencias, **booleano** (Sí / No / vacío), **`options`** (menú con los valores y etiquetas declarados), **fecha** (`SelectorDeFecha`: calendario con clic, flechas, Re Pág / Av Pág y Enter; devuelve `AAAA-MM-DD`, que el editor entiende) y la **ventana de texto** (`VentanaDeTexto`: edita el contenido completo con Aceptar o Ctrl+Enter; en una celda que no se edita solo lo muestra, y para un `jsonb` lo muestra con sangría). Un `jsonb` editable usa la ventana de texto: el expander de JSON de backend-plus intenta editarlo con una variable sin definir. Los campos `clientSide` no tienen ventana de texto. El de **referencias** (`myOwn.ExpanderReferences`, my-tables.js) sirve para los campos con `references` (origen de una FK o softFK) salvo `skipReferenceLookup`: un menú con las filas de la tabla referenciada, su clave y sus campos de nombre (`lookupFields` si la tabla los declara y, si no, los `isName`, que el servidor junta en `nameFields`), ordenadas por esa etiqueta, sin las inactivas (`activeRecords`) y, en una FK compuesta, solo las que coinciden con la fila en las columnas anteriores a la última. Elegir guarda el valor como cualquier edición. Acá: `utils/referencias.ts` (opciones, búsqueda y carga con un cache de 2 minutos; backend-plus lo guarda hasta recargar), `MenuDeOpciones` (lo usan referencias, booleano y `options`: buscar escribiendo, ↑↓, Enter, Escape) y `InputRenderer`; con la celda seleccionada y sin editor, `handleCellKeyDown` abre el editor y le pasa la tecla por la misma cola que F4. Escribir un carácter que el tipo rechaza (una letra en un entero) abre el menú ya filtrado (`autoExpand`).
- `referencesFields`, `skipReferenceLookup`, `nameFields` y `activeRecords` los usa el cliente de backend-plus pero **`backend-plus.d.ts` no los declara**: los tipos locales de `referencias.ts` los describen con intersecciones y guardas, sin casts. Un campo que declara `references` a mano (las asignaciones de dmencu) no tiene `referencesFields`: el valor es la última columna de la clave de la tabla referenciada, como en backend-plus.
- El menú es un modal de MUI: mientras está abierto el editor pierde el foco y eso **no** guarda (`handleBlur` lo ignora), y al cerrarse el foco se devuelve con un `setTimeout`, porque el modal lo retiene hasta desmontarse.
- **Una celda que no se edita también se selecciona al hacer clic** (sin editor; `handleCellClick`): `handleCellMouseDown` cancela la selección por defecto y sin selección F9 no le llega a la grilla, así que el visor de solo lectura no se podía abrir.
- **La lupa** (el icono de `backend-plus` que abre el expander con un clic) es un adorno del editor (`endAdornment` de `InputRenderer`): flecha para los menús, calendario para la fecha y lupa para el texto. Su `onMouseDown` cancela el efecto nativo para que el editor no pierda el foco (perderlo guardaría). En una celda que no se edita no hay lupa: se llega con F9.
- **Los filtros también tienen expanders** (`TypedField` en modo filtro, con el mismo hook `hooks/grid/useExpander.tsx` que usa el editor de la celda): referencias, booleano (Sí / No), `options` y fecha, con F9, Alt+↓ y la lupa, que solo aparece al enfocar el filtro. Lo elegido se escribe como texto del filtro; la fecha como `AAAA-MM-DD`, que `getBestTypedValue` entiende sea cual sea el formato regional. Sin opción vacía (para eso está el operador `∅`) y, en una FK compuesta, sin acotar por la fila (un filtro no tiene fila: `opcionesDeReferencia` con `null`). El booleano en el filtro es un texto como los demás (se escribe s / n, o se elige; el filtro entiende «sí», «no», «1», «0»), no el `Select` de MUI que sigue usando el formulario. La ventana de texto no sirve para filtrar y no está. El editor vertical (`VerticalEditorPage`, también `TypedField`) todavía no los tiene.
- Sin hacer todavía: `inheritFieldsMode`.

### Parámetros de una tabla (dirección y menú, como `backend-plus`)
- `wScreens.table` de `my-menu.js` abre una tabla con lo que declara el ítem de menú y, **encima**, lo de la dirección. Acá lo hace `utils/parametrosDeTabla.ts` (`parametrosDeTabla(item, direccion)`) y lo usan `MenuTablePage` (`/menu/:nombre`) y `GenericDataGridPage` (`/table/:nombre`): `ff` (fixedFields, arreglo `[{fieldName, value, ...}]` u objeto `{campo: valor}`), `fc` (filtros iniciales), `td` (cambios a la definición de la tabla, mezclados en profundidad con `fusionar`, como `changing` de `best-globals`), `pf` y `pick` (viajan en `table_data` como `paramfun` y `pick`, solo si vienen) y `label` (nombre de la pestaña).
- Los parámetros `ff`, `fc`, `td` y `pf` van codificados con `json4all` (`JSON4all.toUrl` / `parse`, que acepta también JSON común). La dirección se lee como `UriSearchToObject` (partir por `&` y por el primer `=`, `decodeURIComponent`), **no** con `URLSearchParams`: ahí un `+` sería un espacio.
- **`fc` / `filterColumns`** (el de la definición del servidor también): `[{column, operator, value}]` es una fila de filtros; con varias filas (arreglo de arreglos, alternativas) **solo se aplica la primera** y se avisa por consola: la grilla tiene una sola fila de filtros. El `.d.ts` de `MenuInfoTable` dice `fieldName` en vez de `column`; el cliente de BP usa `column` y se aceptan las dos. Antes `menuInicial.ts` ponía `td` y `fc` en la dirección y nadie los leía.
- **La ruta de un ítem de menú lleva sus grupos: `/menu/<grupo>/.../<nombre>`** (`rutaDeTablaDeMenu`, `gruposDeItem`, `itemDeRuta` en `utils/menuInicial.ts`; la ruta es `/menu/*`). Los `name` se repiten entre grupos: en dmencu «encuestador», «recuperador», «ingresador» y «supervisor» están en asignación (`t_encu_areas`...) y en recepción (`encuestadores_asignados`...), con tablas distintas. Con `/menu/:nombre` se buscaba el primer ítem con ese nombre: recepción abría la tabla de asignación (sin sus detalles ni la columna de acciones, `clientSide` de `tareas_tem_recepcion`) y el menú marcaba los dos ítems. Los segmentos van con `encodeURIComponent`. Una dirección vieja `/menu/<nombre>` cae en la primera tabla con ese nombre. Quien arma la ruta de un ítem tiene que pasarle sus grupos (`SideMenu` los lleva por `MenuListItem`; la pantalla de inicio los calcula con `gruposDeItem`).
- **fixedFields** (`utils/fixedFields.ts`, igual que `TableConnector`): uno que fija el valor oculta su columna (salvo `show`), no se edita y no se filtra; uno con `range` o `until` es un rango: la columna se ve, se edita y se filtra.

### Anchos de columna
- Como `backend-plus` (`fieldDef.width` en `my-tables.js`, «Width in pixels for the grid» en el `.d.ts`), el `width` que declara el backend para un campo manda sobre el que se calcula con el título y los datos (`calcularAnchosDeColumnas`). Sin `width` se calcula. Las columnas se pueden arrastrar desde el borde del encabezado (`resizable`, con `columnWidths` en el estado de la grilla); en `backend-plus` el `width` también es el mínimo, acá el usuario puede achicarla.

### Columnas ocultas (`hiddenColumns`, como `backend-plus`)
- Una grilla abre con ocultas las `hiddenColumns` de la definición (el servidor suma ahí los campos `isName: 'known'`, `table-def-adapt.js`; `utils/columnasOcultas.ts`, `columnasOcultasIniciales`). **Un campo con `visible: false` es otra cosa: viaja en la definición pero no se dibuja nunca** (`campoDibujable`): no es una columna oculta que el usuario pueda mostrar, así que no está en el diálogo ni se exporta (`backend-plus` lo trata como oculta; acá se decidió que nunca se vea). Si el menú o la dirección pasan `td` con `hiddenColumns`, se aplica porque la definición ya viene mezclada. Antes `useGridColumns` ignoraba `hiddenColumns`.
- El estado es `columnasOcultas` de `GenericDataGrid` (se guarda en el cache de los detalles). Cambiarlo sí rearma las columnas, pero solo lo cambia el usuario: **Alt+clic en el encabezado** oculta (`defaultColumnHeaderCellRenderer`, en la captura para que react-data-grid no ordene) y **«ocultar o mostrar columnas»** del menú abre `DialogoDeColumnas` (a la izquierda las que se ven, a la derecha las ocultas; un clic cambia de lado). No lista las que oculta un fixedField, que no se pueden mostrar.
- La exportación no incluye las ocultas salvo la opción `hiddens` (`ExportDialog`). El editor vertical (`VerticalEditorPage`, recibe `columnasOcultas`) tampoco muestra ni los `visible: false` ni las ocultas, como el modo vertical de `backend-plus`. Los detalles desplegados son otra `GenericDataGrid`: cada uno lleva sus propias columnas ocultas.

### Menú lateral (`SideMenu`)
- **Acordeón**: abrir un grupo cierra a sus hermanos (con lo que tengan abierto adentro, `abrirGrupo`); al navegar queda abierto solo el camino del ítem que se muestra (`abrirCamino`). El estado abierto/cerrado se guarda por el **camino** del grupo (`asignacion/encuestador`, `claveDeMenu`), no por su nombre: los nombres se repiten entre grupos.
- **Buscador** arriba, fijo junto con el logo (solo scrollea la lista): palabras sueltas, sin tildes ni mayúsculas, en la etiqueta del ítem **o de sus grupos** (`utils/busquedaDeMenu.ts`); los resultados llevan debajo el camino de grupos. ↑ ↓ Enter Escape; **Ctrl+K** lo enfoca desde cualquier pantalla (abre el menú si está cerrado).
- **Recientes**: las últimas 4 pantallas (`localStorage`, `fpr.menu.recientes`). Un ítem que ya está **no cambia de lugar**, y ahí no se hace `scrollIntoView`: se hizo las dos cosas y el menú saltaba al principio al elegir un ítem.
- Íconos grises; el ítem seleccionado y el grupo abierto toman el color de su tipo. Una wScreen se considera implementada si está en `myWScreens` **o** si el puente está encendido (se pide a backend-plus); el triángulo de advertencia es solo para «no implementada». Las pantallas del puente viven en `/bp/menu#w=<pantalla>`: así se detecta cuál está seleccionada.

### Estilo alineado con el skin `modern` de backend-skins
- Para que lo que entra por el puente se parezca: bordes `#e0e0e0`, encabezado `#eceff1` con letra de peso 500, hover y selección con el color primario translúcido (variables `--rdg-*` de `.rdg-light` en `GenericDataGrid.css`; usan `--primary-rgb` del skin si está cargado). Los íconos de acciones de la grilla son grises sin borde (toman su color al pasar el mouse), como `.table-button`. Al scrollear, detrás de las filas hay un patrón de filas vacías (`background-image` de `.rdg-light`, 30 px) para que no se vea blanco mientras React dibuja las filas virtualizadas, y `content-visibility: visible` (react-data-grid lo pone en `auto`). Por eso los colores de hover y selección tienen que ser **opacos** (`color-mix` con blanco): uno translúcido deja ver el patrón como una raya en la fila. Sigue distinto: la barra azul del título de cada grilla y los íconos (acá son los de MUI).

### Cambiar contraseña y recuperar clave
- **Cambiar contraseña** (`/chpass`, `CambiarClavePage`; ícono de llave junto a «Salir»): `POST /chpass` con `oldPassword`, `newPassword` y `repPassword`, como el formulario de backend-plus. El servidor contesta con una redirección: al login si cambió (y **cierra la sesión**) o de vuelta a `/chpass` con el motivo en la página (`.error-message`, `resultadoDeCambioDeClave`; depende del HTML de `chpass.jade`).
- **«Me olvidé la clave»** en el login es opcional: prop `recuperarClave` de `App` (`true` = `/new-pass`, o la ruta de `login.forget.urlPath`). Es un enlace a la página del backend; el mail y el formulario siguen siendo del servidor, y al terminar queda en el login del servidor, no en el de React.

### Sesión y arranque
- Con el estado todavía sin cargar (`idle`), `PrivateRoute` manda a `/login` guardando la ruta pedida; `InitialRedirectHandler` (montado fuera de las rutas privadas) vuelve a esa ruta cuando la sesión resulta válida. Tiene una guarda para no caer en la pantalla de inicio mientras la ruta guardada se limpia.
- **No hay `HomePage` ni ruta `/home`: la pantalla de inicio la define el backend, como en `backend-plus`.** `/` (`PantallaInicial`) redirige al ítem de menú con `selectedByDefault` (y, si es un grupo, al que lo declare adentro; `itemInicial`, `rutaDeItemDeMenu` en `utils/menuInicial.ts`, que también arma las rutas del menú lateral). Si el backend no declara ninguno, `/` queda vacía, igual que en `backend-plus`. El login y `InitialRedirectHandler` mandan a `/`. Una aplicación que quiera otra pantalla de inicio la declara en su menú.
- El cartel «¡Sesión expirada!» solo corresponde si hubo una sesión (guardada de la visita anterior o activa en esta carga). En la primera visita sin sesión, ir al login no lleva cartel.
- **Cierre de sesión a propósito** (Salir, cambiar la contraseña): no es una sesión expirada (no hay cartel) y **no se recuerda la pantalla** para volver a ella (`utils/cierreVoluntario.ts`, solo en memoria y hasta volver a iniciar sesión; si se guardara, un enlace abierto después de recargar no se recordaría). La pantalla solo se recuerda si se abre un enlace sin sesión o si la cookie se venció.
- **Cookie vencida**: al volver a ingresar solo vuelve a su pantalla **el mismo usuario** (`redirectUsername` en el router; `AppContext` lo anota al perder la sesión). Una ruta que se pidió sin haber tenido sesión (un enlace compartido) no tiene usuario: vale para cualquiera.
- Enter en un campo del login ingresa directamente (no pasa el foco al botón).

## Puente con el cliente de backend-plus (opcional, `src/puente/`)

Para no perder lo que la grilla de `backend-plus` ya hace y que acá todavía no está: la aplicación pasa `puenteBP` a `App` y las wScreens que **no** registró en `myWScreens` se piden al cliente de `backend-plus` (`myOwn.wScreens[nombre]`), en lugar de mostrar «no implementada». `GrillaBP` pone `myOwn.tableGrid` dentro de una página React; `/bp/table/:tableName` sirve para comparar las dos grillas. Lo propio de React siempre tiene prioridad.

- **Mismo origen que el backend, obligatoriamente.** Los scripts de `backend-plus` solo se sirven con sesión (sin ella redirigen al login) y su cliente es un singleton global (`myOwn`, `my`). La aplicación se sirve bajo `<base-url>/react/` o, en desarrollo, Vite hace de proxy (ver `mi-frontend`: `VITE_BASE=/ggs2026/react/ VITE_BACKEND_URL=/ggs2026 PROXY_BACKEND=http://localhost:3044`).
- `cargarClienteBP` lee la página `<base-url>/menu`, saca de ahí los `<script>` y `<link>` (los arma el servidor con `clientIncludes`, en orden) y los carga. Es un atajo: lo sano sería que el servidor exponga esa lista, y eso es cambiar `backend-plus` (consultar antes).
- Tres cosas que el cliente de `backend-plus` necesita y que el puente hace: un `<base href>` en la base-url (arma sus direcciones relativas a la página), el global `my` igual a `myOwn`, y llamar a `myOwn.autoSetup()` a mano (él lo hace al evento `load`, que ya pasó).
- Una wScreen de `backend-plus` puede ser una función, un objeto con `mainFunction`, o un objeto con `parameters` y `mainAction` (como `abrir_encuesta` de dmencu: muestra el formulario de parámetros). `resolverPantallaBP` reproduce el `showPage` de my-menu.js para las tres.
- **Las pantallas de `backend-plus` viven en una sola ruta, `/bp/menu#w=<pantalla>&...`** (`PaginaBP`; `/wScreens-fallback/:nombre` redirige ahí). Se parece a `<base-url>/menu` **a propósito**: BP y las aplicaciones arman direcciones a partir de la ubicación (`location.origin + location.pathname + '/../menu#w=...'` en un `history.replaceState` + `location.reload()`, como el «Cerrar» de una encuesta de dmencu; `location.pathname + '#w=...'` para abrir en otra pestaña) y así caen en esta misma ruta, que lee los parámetros del hash (o de la query) como BP. Con otra ruta, esas direcciones salen de `/react`. En producción, el servidor tiene que devolver el `index.html` también para `/react/bp/menu`.
- **Lo que BP manda a páginas del backend se resuelve adentro** (`capturaDeNavegacion.ts`, montado una sola vez por `CapturaBP` mientras el puente está encendido, **no** solo mientras hay una pantalla de BP: su cliente sigue vivo después de salir de ella y sus avisos quedan en el `body`; por ejemplo el de «Iniciar sesión» de `my-inform-net-status.js`, un `<a href="login">` que sin la captura llevaba a `<base-url>/login` y, con la sesión abierta, a `<base-url>/menu`, el BP nativo): clics en `<a>` (a nivel documento, también en diálogos) y, donde existe la Navigation API, cualquier `location.href = ...`. `rutaDeEnlaceBP` traduce `<base-url>/menu#w=...` a `/bp/menu#w=...`, y `login`/`logout` a los de la aplicación. El clic se corta con `stopPropagation`: el botón «proceder» de BP tiene además un `onclick` propio (`history.pushState` a `<base-url>/menu#...` y `showPage`) que dejaría la URL fuera de la aplicación y daría un error de BP. También se traduce `history.replaceState`: al editar un parámetro de una pantalla (`myOwn.replaceAddrParams`) BP reescribe la dirección a `menu#...` y, con el `<base>`, la aplicación quedaba en `<base-url>/menu` (un F5 y se salía de `/react`); `replaceState` no pasa por la Navigation API. También se traduce `window.open`: el código de las aplicaciones arma la dirección de otra pestaña como `location.origin + location.pathname + '#w=...'` (`my.menuSeparator` es `'#'`; los botones «abrir» de dmencu: `abrir_encuesta`). En BP el `pathname` siempre es `<base-url>/menu`, acá es la ruta actual (una grilla, que ignora el hash): `rutaDeHashDeBP` lleva cualquier dirección de la aplicación con `#w=` a `/bp/menu#w=...`. Lo que el hash no cubre: `location.href = pathname + '#w=...'` en la misma pestaña (solo cambia el hash, no navega). Los enlaces `menu#i=...` (ítems del menú de BP, sin `w`) no se traducen. Los parámetros se leen con `myOwn.UriSearchToObject`, no con `URLSearchParams`: `up`, `ff` y `detailing` tienen su propio formato y llegan como objetos.
- **Los scripts de `backend-plus` se inyectan recién cuando la ventana terminó de cargar** (`esperarCargaDeVentana`): su `load` ejecuta `showPage`, que acá falla (no hay `#total-layout`). Y su manejador de errores (`myOwn.log`) deja el mensaje como primer hijo del `body` cuando no hay un `#mini-console`, lo que **corre toda la aplicación hacia abajo** durante 30 s. Era el «espacio entre el menú y el contenido» que aparecía con F5 y a veces no.
- **La aplicación no está atada a la ruta `/react`.** `my-menu.js` escucha `popstate` y, si la dirección no termina en `/react`, ejecuta `showPage()` (falla igual que el `load`); lo marca como `//TODO: desacoplar de BP`. El puente lo evita sin tocar `backend-plus`: mientras inyecta los scripts, `sinEscuchasDeVentana(['popstate'], ...)` ignora que registren ese evento (la navegación es del router). Si backend-plus agrega otro enganche así, se ve como un error en `ConsolaBP`. Sin el puente (`puenteBP` apagado) no se carga nada de `backend-plus` y la base-url de la aplicación es la que quiera. **Sin probar en navegador** (se probó el filtro en Vitest; falta atrás/adelante contra un backend real).
- **`ConsolaBP`** ofrece ese `#mini-console` (dentro de `PantallaBP` y `GrillaBP`): los mensajes y errores de `backend-plus` se ven como avisos flotantes arriba a la derecha, debajo de la AppBar, sin ocupar lugar. BP registra algunos errores **dos veces** (el de una llamada ajax lo registra `my-ajax.js` y el `catch` de «proceder», en `my-menu.js`, lo repite; pasa también en BP nativo): si llega un aviso igual a uno que llegó hace menos de 1 s, se descarta (`descartarRepetidos`). Sin contador: el error se ve una vez. Las hojas de estilo del backend y de las aplicaciones también estilizan `#mini-console` (por id, con `top`, `width: 100%`, `max-height`...): por eso `ConsolaBP` usa `&#mini-console` y repone esos valores.
- Las wScreens de `backend-plus` dibujan en `#main_layout`: `PantallaBP` le da ese contenedor y le pasa lo que declara su ítem de menú más la query string. Mientras está montada no puede haber otro elemento con ese id.
- **clientSides de las grillas.** Se reproducen los de `myOwn.clientSides` de backend-plus que no dependen de su DOM: `displayUrl` (un enlace) y `newPass`. `newPass` no tiene componente: es una celda común con el mismo editor y las mismas teclas, y al terminar de editar corre `guardadosPropios.newPass` (`admin_chpass`) en lugar de `table_record_save` (`InputRenderer`); la fila no cambia, no se ve lo escrito. Un campo clientSide **no es editable** (`campoEditableEnCelda`) salvo que tenga guardado propio: antes la columna era editable (`editable !== false`) y Enter abría el editor, que guardaba `clave_nueva` con `table_record_save` («no existe la columna clave_nueva en la relación usuarios»). `$lock` usa la base local del modo offline y no está. Si una tabla tiene un clientSide de campo que se dibuja y no está registrado, o uno de **tabla** (`TableDefinition.clientSide`, que acá no se reproduce), y el puente está encendido, `GenericDataGrid` muestra la grilla de backend-plus (`GrillaBP`) en lugar de la propia (`clientSidesSinImplementar`); la grilla de BP va dentro de un contenedor con su propio scroll y 8 px de margen: el panel de `GenericDataGridPage` tiene alto fijo y `overflow: hidden` (las grillas de esta librería se miden solas) y recortaba la de BP, que crece con su contenido. Sin puente queda el `FallbackClientSideRenderer` de siempre. Lo que registra la aplicación con `extendClientSides` evita el cambio. Sin probar en navegador.
- **Las hojas de estilo de backend-plus son globales** (`body { font-family: arial; font-size: 93.75%; margin: 0 }` de `my-menu` y `my-things`, los skins...) y cargadas con un `<link>` cambiaban la fuente y el aspecto de toda la aplicación (el menú incluido), antes y después de abrir una pantalla de BP. Ahora `cargarClienteBP` las baja como texto y `acotarEstilos` (`estilosBP.ts`) prefija cada selector con `:where(.fpr-bp)` (`.fpr-bp` es la clase del contenedor; **`:where` no suma especificidad**: con `.fpr-bp` a secas, `button { }` de BP pasaba a ganarle a las clases de MUI de lo que corre adentro, como el tablero de dmencu, y pisaba sus tamaños, botones y enlaces), la clase del contenedor de `PantallaBP` y `GrillaBP`; `html`, `body` y `:root` pasan a ser el contenedor (sin su `overflow`, alto ni `position`: `body { height: 100%; overflow: hidden }` le cortaría el contenido y la grilla no scrollearía). Las reglas de los skins empiezan con `[my-skin=default] ...` y `my-skin` es un atributo del `body` (`lib/my-skin.js`): se aplican al contenedor, que lo recibe con `copiarSkinAlContenedor`; sin eso se pierde todo el skin. `@font-face` y `@keyframes` no se tocan y las `url()` relativas se resuelven contra la hoja. Lo que BP agrega fuera del contenedor (diálogos que cuelgan del `body`) queda sin sus estilos. Sin probar en navegador.
- `rutaBase` (`src/rutaBase.ts`) toma el `base` del bundler: es el `basename` del router y el prefijo de las pestañas nuevas (Ctrl+click en un detalle `wScreen`).
- **No hay un entorno de prueba automático para esto**: jsdom no carga los scripts de `backend-plus`. Los tests cubren la extracción de recursos y la elección de pantalla; el resto se prueba en el navegador contra un backend real (headless: Chrome con `--screenshot` y un proxy chico que inyecte la cookie de sesión).
- Probado contra ggs (con Chrome controlado por el protocolo de depuración, sin escribir en la base): grilla `usuarios`, la wScreen `ayuda` y `abrir_encuesta` hasta ver el formulario de la encuesta de dmencu dentro de `mi-frontend`. Sin probar: edición, detalles anidados, exportar y la convivencia del CSS global de `backend-plus` con MUI.

## Compilación y fuentes en F12

- `npm run build` (tsup, config en `tsup.config.ts`) genera `dist/` en ESM y CJS con `.d.ts`. **Sin `--splitting`**: con una sola entrada el `.map` de CJS sale roto. Los `.map` llevan el código fuente adentro (`sourcesContent`): en F12 se ven los `.ts`/`.tsx` originales.
- Las dependencias y `peerDependencies` quedan externas; las resuelve el bundler de la aplicación.
- `mi-frontend` tiene un plugin de Vite que encadena el `.map` de esta librería en el build de la aplicación (Rollup no lo hace solo).
- ⚠️ `npm install` dentro de una aplicación enlazada (`mi-frontend`) **reemplaza el `npm link`** y pisa `dist/` y `package.json` de esta carpeta con lo publicado. Después hay que rehacer el enlace (en Windows, `mklink /J`) y volver a compilar.

## Tests

- **Framework**: Vitest + jsdom + Testing Library. **Comandos**: `npm test` (una pasada), `npx vitest` (modo vigilancia), `npm run typecheck`.
- Los tests viven al lado de lo que prueban (`*.test.ts` / `*.test.tsx`) y están en castellano. La preparación común está en `src/test/preparacion.ts`.
- Se cubren las funcionalidades críticas y, sobre todo, **cada bug que se arregla lleva su test**: se verifica que falle si se reintroduce el bug. Hoy (243 casos): codificación de parámetros, el menú (búsqueda), el cambio de contraseña y a dónde se vuelve tras ingresar, fixedFields de los detalles, detalle wScreen y `condition`, `PantallaDeRuta`, `ff` del menú, el store de la grilla, la vista de datos (orden, filtros, edición en el lugar), la edición con filtro, la cola de F4, la vuelta a la ruta pedida tras el login, el cartel de sesión expirada y los helpers.
- jsdom no calcula medidas ni trae `ResizeObserver`: lo que depende del layout (alturas, anchos, virtualización) se prueba en el navegador con `mi-frontend`, no en Vitest.
- Para el mock de `fetch` y de `fetchApi` usar `vi.stubGlobal` / `vi.mock`; no levantar servidores en los tests.
- Antes de commitear: `npm run typecheck`, `npm test` y `npm run build`.

### Pruebas en el navegador con un backend real
- `mi-frontend` sirve para probar con una aplicación real: `VITE_BACKEND_URL=/dmencu PROXY_BACKEND=http://localhost:3050 npx vite`. Con una ruta en `VITE_BACKEND_URL`, Vite hace de proxy y el navegador habla con un solo origen (el backend solo habilita CORS si tiene `server.allowedHosts`). En Git Bash agregar `MSYS_NO_PATHCONV=1` o la ruta se convierte en una ruta de Windows.
- Las credenciales de prueba se las da el usuario en el chat; **no escribirlas en archivos ni en la documentación**. Las pruebas contra una base real son de solo lectura salvo que el usuario diga otra cosa, y lo que se escriba se deja como estaba.
- Para medir rendimiento usar el build de producción: en desarrollo React valida de más y los tiempos engañan.

## Publicación en npm

Es automática, igual que `dmencu`: `.github/workflows/publish.yml` llama al workflow reutilizable `codenautas/.github@v3` (`npm ci`, `npm run build`, tests y `npm publish`). No hay token: npm confía en el repo (Trusted Publisher configurado en npmjs.com para `codenautas/frontend-plus-react`, workflow `publish.yml`, sin environment).

Para publicar una versión (solo cuando el usuario lo pide):
1. Subir la versión: `npm version X.Y.Z --no-git-tag-version` (toca `package.json` y `package-lock.json`; npm no deja republicar un número ya publicado).
2. Commit y `git push origin main`.
3. Crear y subir el tag: `git tag -a vX.Y.Z -m vX.Y.Z && git push origin vX.Y.Z`. El tag tiene que coincidir con la versión de `package.json` o el workflow falla.
4. Verificar en la pestaña Actions de GitHub y con `npm view frontend-plus-react version`. En esta máquina no está `gh`.

- Alternativa: correr el workflow a mano desde Actions en `main` (crea él mismo el tag `v<versión>`).
- Las versiones con `beta`, `alpha` o `rc` en el número se publican con ese dist-tag, no como `latest`.
- `package.json` necesita el campo `repository`; sin él npm no valida la publicación.
- `npm ci` exige el lock sincronizado: probar con `npm ci --dry-run` antes de taguear.

## Cuándo parar y preguntar

- Si hace falta cambiar `backend-plus` para que algo ande: parar. Casi siempre hay un punto de extensión (o el cambio va en el protocolo del cliente).
- Si una propiedad de `TableDefinition`, `FieldDefinition` o `ProcedureDef` no aparece en `backend-plus.d.ts`: no inventarla.
- Si el comportamiento observado difiere de `backend-plus`: avisar de la diferencia en lugar de resolverla en silencio.
- No publicar en npm ni subir tags sin que el usuario lo pida.
